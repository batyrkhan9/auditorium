# The screen is a small Python web app with server-rendered HTML

**Decided:** Starlette, Jinja2 templates and uvicorn, all in Python, in the same
uv workspace as the contract. Pages are rendered on the server. The only
JavaScript is a filter dropdown that submits itself. No Node, no build step.

**Considered:**

- React or another single-page app over a JSON API. Better for heavy
  interaction, but it adds a Node toolchain and a second copy of the contract
  types (from `contracts/schema/`) that can drift from the Python models.
- FastAPI. Built on Starlette, and its main gains (request validation, OpenAPI
  docs) serve a JSON API, which we do not have.
- `http.server` from the standard library. No dependencies, but we would write
  our own routing, form handling and test client.
- Streamlit. Quick to start, but hard to control layout. Its rerun model also
  fits poorly with an append-only log written through `LogWriter`.

**Why:** the screen must use the contract's own code: `load_run`,
`verify_evidence` and `LogWriter.sign_off`. Then what the auditor sees is
checked by the same functions the eval uses, and sign-offs keep the hash chain
intact. Staying in Python makes that a function call. Rendering on the server
keeps the app to one process with three runtime dependencies, and Starlette's
test client lets us test every page in pytest.

**What would change our mind:** if reviewers need rich interaction (bulk
sign-off, side-by-side document viewing, live updates while a run is in
progress), or if the screen must be hosted for Ramp separately from the Python
code. Then a JSON API plus a small front end would be worth the build step.
